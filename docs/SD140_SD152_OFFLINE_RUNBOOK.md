## Boundary

- `sd140_offline_swing_controller.OfflineSwingCycleController` accepts exactly SD-074 authenticated runtime and the SD-138 fake-only adapter, never an arbitrary broker transport. All policy, owner-test-grant, quote, order/position lineage and audit checks stay in their existing modules. It does not admit new strategies and does not generate trading opportunities.
- `sd152_offline_swing_runner.OfflineSwingScheduledService` uses SD-068's existing `XNYS` `swing_review` job and requires explicit **SIMULATION_ONLY** configuration at both track and exchange levels. `RESEARCH_ONLY` (the default) is refused before a cycle.
- The separate SD-152 durable SQLite single-writer fence binds a unique `slot` and `token` before claiming the SD-068 scheduler job. A second process cannot claim an already running cycle or repeat a previously completed slot. A process crash leaves `RUNNING`; an ambiguous or failed cycle leaves `UNRESOLVED`. Neither state has an automatic expiry or takeover. This is a **fail-closed first slice**, not production-grade liveness/recovery.
- **SD-152 health and operator visibility (28 October continuation):** `OfflineSwingRunFence.heartbeat(token, owner, at)` updates SQLite only for the *current matching* worker, rejecting forged tokens, changed owners and regressing clocks. `OfflineSwingRunFence.health(now)` flags stale RUNNING workers and unresolved incidents; it never grants lease takeover or authorises another trade. `OfflineSwingScheduledService.inspect(now)` reports local policy kill, pending/unknown durable order counts and SideDeck-owned positions. **This is NOT independently broker-verified account health.** Malformed idle/worker records fail closed. No external alerts, live broker calls or reset facility were added.
- SWING exits have priority over entries; only the verified SideDeck-owned, full reduce-only close is allowed. No new entry when an exit was due, open positions are still being monitored, risk alerts appear, the kill switch is engaged, or a fresh independently sealed send quote is unavailable.
- The adapter is **simulation only**. The historical eToro Demo release is `NOT_RELEASED`; the owner kill switch remains `HALTED`. No API keys, broker or market-data requests, network clients, remote deployment or actual Demo orders are used or authorised.

## Recovery / operator protocol (offline only)

1. Inspect the read-only `OfflineSwingScheduledService.inspect(now)` and `OfflineSwingRunFence.health(now)` status, along with SD-068 `SchedulerStore.history("swing_review")`, SD-063 incidents and SD-129/036 durable lineage. **Stale heartbeat means investigate, never take over**; the local status is not an eToro /pnl read and cannot prove broker flatness.
2. If fence is `RUNNING` on startup or `UNRESOLVED` after a failed cycle, **stop further ticks**. Confirm which prior OPEN/CLOSE POST, if any, reached the fake broker. Use only independently scoped, audited GET-only recovery, never another POST with the same or a new identity for an ambiguous intent.
3. Reconcile any open or pending positions, exactly four original protected baseline positions, grants, anchors, fill/close evidence and policy HALT. Do not automatically clear the kill switch or overwrite the original baseline.
4. This slice **intentionally provides no automatic recovery/clear-unresolved action**. A future independently reviewed operator-only reconciliation + signed recovery protocol is required before safe unattended restart/deployment; hand-editing the SQLite fence is prohibited as an operational procedure.
5. Do not interpret a green offline run as a genuine strategy qualification, real broker economics or a live pilot.

It returns **zero broker requests**, no grants, no recovery authority and no release/reset action; its `broker_account_verified` field is **false**. This is an operator *request plan*, never a brokerage source of truth.
- An `OPEN` with no trusted accepted orderId: request a separately signed, audited **GET by the original order reference**. Never infer order failure from a 404 and never repeat POST. An accepted opening with a durable orderId can be independently checked by reference and, after an initial 404, by that saved orderId.
- The SD-138 offline fake recovery path now reauthorises a **separate read reference** for exactly one follow-up GET by durable accepted orderId if the first GET returned a simulated 404. Neither GET reopens the position or clears owner HALT; if both return 404, state remains unresolved and no third GET/POST is sent. This offline fixture currently has no audited wall-clock wait interval; real HTTP timing/backoff and provider rate limits **remain blocked for future review**, and cannot be inferred from these fixtures.
- A `CLOSE` with `OUTCOME_UNKNOWN` or `PENDING_SUBMIT` and **no accepted close orderId** must receive separately authorised, baseline-verified whole-account reconciliation; broker close-info cannot be invented. A persisted accepted CLOSE with orderId requires **signed close-info GET followed by independently authorised /pnl** and matching original four-position baseline before a full close may be classified. Both routes forbid any replacement close POST.
- `run_due()` checks the durable SD-036 uncertainties **even if the SD-152 singleton fence is IDLE**. An orphaned open reservation, unresolved close or an accepted close awaiting reconciliation returns `RECOVERY_REQUIRED` without consuming a schedule slot or making any simulated broker call. The owner release remains locked.
- Revocation tested between recovery reads: if the synthetic owner grant is revoked after referenceId GET returns 404, authorisation for the orderId fallback fails, **so no second GET and no further POST**. Existing HALT stays engaged; accepted order identity remains durably recorded. This is verified at code/test `78093d3ca9db39f37f6324fe95cb8e1bedf36848`, [CI 40658615619 PASS](https://github.com/smbabalola/sidedeck/actions/runs/40658615619): **1,908 passed / 2 skipped**, Ruff, mypy (206 source files), Alembic, dashboard and browser E2E.

## SD-140/141 offline fill and policy-expiry resilience (28 October 2026)

**Latest code/test `ce08b2c56136b5cd032861998730089a0a356d90`:** [exact-head CI 40659971529 PASS](https://github.com/smbabalola/sidedeck/actions/runs/40659971529), **1,915 passed / 2 skipped**, Ruff, mypy (206 source files), SQLite Alembic, frontend and browser E2E. Baseline before this extension: `78093d3` [CI 40658615619 PASS](https://github.com/smbabalola/sidedeck/actions/runs/40658615619) (1,908/2). A first test-only run `8e662d9` was red only due to an incorrect tuple-vs-list assertion (`lineage.owned_positions()` returns a list); corrected in `84af944` [CI 40659690917 PASS](https://github.com/smbabalola/sidedeck/actions/runs/40659690917) (1,912/2).

- **A complete opening order split over multiple distinct broker position IDs:** strict SD-129 lookup refuses to bind one arbitrary position as SideDeck-owned. The SD-138 fake adapter durably HALTs, leaves accepted order lineage available for separate reconciliation, and issues only the original open POST. No premature portfolio/`/pnl` flatness claim.
- **One terminal partially filled opening order:** SideDeck records the exact filled/remaining units in a single verified position and generates a full reduce-only close of **that actual owned quantity**, not the requested quantity. The fake broker's final whole-account `/pnl` still must match the four original protected positions.
- **Partially filled close after restart:** the close-info GET alone cannot prove the owned position flat. The attempted restart recovery fails closed, keeps the close accepted-but-unresolved and the original position open, and does **not** request final `/pnl` or repeat a close POST.
- **Original SWING policy expires with a position open:** with a *separately synthetic owner-signed protective grant* that remains valid, SD-063 proposes a `PROTECTIVE_FLATTEN` reduce-only close. Both the SD-138 fake broker and SD-140 exit-first controller confirm a full close only after fresh signed planning and send-time quotes, close-info and independent fake whole-account `/pnl`. No new entry is authorised by the protective grant; `ETORO_DEMO=NOT_RELEASED` is unchanged.
- **Missing or revoked protective grant after expiry:** the policy produces an expiry/revocation alert, not a close authority; the controller durably HALTs with an owned position pending operator action, sends no close POST and cannot invent a fill. This intentionally does **not** solve the operational problem of an uncovered position after protective authority expires: owner-controlled grant renewal, monitoring and escalation remain required.
- All of the above used **deterministic offline fixtures and synthetic grants only**. No real market data was fetched, no eToro Demo/Real API call was sent, no portfolio was touched, and no independent security release occurred.
